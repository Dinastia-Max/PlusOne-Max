# ПлюсОдин

Мини-приложение в MAX, в котором можно найти любительскую футбольную игру
рядом, записаться на неё или собрать свою.

MVP работает с футболом в СВАО Москвы. Пользователь видит игры на ближайшие
семь дней, состав и свободные места. Организатор выбирает площадку из базы,
задаёт время и размер состава. Система уведомлений подтверждает запись,
напоминает об игре и сообщает об отмене, когда запущен `notification-worker`.

Репозиторий: <https://github.com/Dinastia-Max/PlusOne-Max>

Если репозиторий остаётся приватным, перед проверкой нужно выдать организаторам
доступ. Без авторизации GitHub возвращает `404`, даже если ссылка указана верно.

Рабочий стенд:

- бот MAX: <https://max.ru/t116_hakaton_max_bot>;
- mini-app: <https://plusone-max.onrender.com/>;
- документация API: <https://plusone-api-os3a.onrender.com/docs>.

Для полного пользовательского сценария открывайте mini-app через бота MAX:
обычная вкладка браузера не передаёт подписанные данные пользователя.

Проверяемая версия должна быть зафиксирована commit hash, указанным в заявке на
сдачу. Проверить hash локально:

```bash
git rev-parse HEAD
```

После дедлайна для проверки нужно использовать именно этот commit.

## Текущий стенд

На момент последней проверки компоненты размещены так:

| Компонент | Где работает | Когда доступен |
| --- | --- | --- |
| frontend | Render Static Site | постоянно |
| API | Render Docker Service | постоянно |
| PostgreSQL | Render PostgreSQL | постоянно |
| бот | отдельный Long Polling-процесс | пока запущен процесс |
| `notification-worker` | отдельный процесс | пока запущен процесс |

Frontend обращается к публичному адресу API, а API подключается к PostgreSQL по
`DATABASE_URL`. Интерфейс и публичные методы API можно проверить без локального
запуска. Для полного сценария через MAX должны одновременно работать бот и
`notification-worker`.

Бот и обработчик уведомлений не входят в три постоянно работающих сервиса
Render. Сейчас они запускаются отдельно и остановятся при выключении компьютера
или завершении процессов. Бот через Long Polling отвечает на `/start` и
показывает кнопку mini-app. `notification-worker` читает очередь из PostgreSQL и
отправляет сообщения через MAX Bot API. Для постоянной работы его можно
развернуть на Render по готовому `render.yaml`.

## Что реализовано

Сценарий игрока:

1. Открыть бота в MAX и нажать «Открыть приложение».
2. Посмотреть игры на ближайшие семь дней.
3. Открыть карточку: время, площадка, состав, минимальное число игроков и мяч.
4. Записаться или отказаться от участия.
5. Найти запись в разделе «Мои игры».
6. Получить подтверждение и напоминания в чате MAX.

Сценарий организатора:

1. Нажать «Создать игру».
2. Выбрать площадку из базы, дату, время, длительность и размер состава.
3. Указать телефон с согласием на показ участникам или не указывать контакт.
4. Посмотреть записавшихся и при необходимости отменить игру.

Сервер не допускает повторную запись, запись в заполненную, начавшуюся или
отменённую игру и запись в две пересекающиеся по времени игры. Игры,
соприкасающиеся только границами времени, разрешены.

## Архитектура

Схема ниже показывает локальный запуск через Docker Compose. На Render frontend
и API развёрнуты отдельными сервисами: адрес API передаётся frontend во время
сборки через `VITE_API_URL`.

```text
Пользователь MAX
       │
       ▼
MAX Bot API ◄──────── уведомления ─────── notification-worker
       │                                      ▲
       │ open_app                             │ notification_jobs
       ▼                                      │
React mini-app ── /api ──► nginx ──► FastAPI ─┴─► PostgreSQL
       │                                  │
       └── X-Max-Init-Data ───────────────┘
```

Компоненты:

- `miniapp` — собирает React/Vite-приложение, раздаёт его через nginx и
  проксирует `/api` на backend;
- `backend` — FastAPI, проверка `initData`, бизнес-правила и REST API;
- `postgres` — площадки, слоты, участия и очередь уведомлений;
- `bot` — точка входа в MAX, команда `/start`, кнопка открытия приложения;
- `notification-worker` — забирает задания из PostgreSQL и отправляет сообщения
  через MAX Bot API;
- `backend-test` и `test-postgres` — изолированный контур тестирования,
  включаемый профилем `test`.

Активное мини-приложение находится в `frontend/`. Файл `miniapp/index.html` —
ранний статический прототип и в `compose.yaml` не используется.

## Требования

- Docker Desktop или Docker Engine с Docker Compose v2;
- Git;
- бот и мини-приложение, созданные на платформе MAX;
- токен бота MAX;
- публичный HTTPS-адрес для проверки внутри MAX.

Python, Node.js, pnpm и PostgreSQL на хост устанавливать не нужно: они находятся
в Docker-образах.

Для публикации локального порта по HTTPS можно использовать Cloudflare Tunnel.
`cloudflared` не входит в Docker Compose и устанавливается отдельно. Он нужен
только для доступа к локальному mini-app из MAX.

## Локальный запуск

### 1. Создать файл окружения

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

Linux/macOS:

```bash
cp .env.example .env
```

Минимально заполните `.env`:

```env
MAX_BOT_TOKEN=<токен бота MAX>
MAX_MINI_APP_URL=<публичный HTTPS-адрес mini-app>
```

Токен нельзя коммитить. `.env` исключён из Git.

### 2. Запустить все локальные компоненты одной командой

```bash
docker compose up --build -d
```

При старте backend автоматически выполняет `alembic upgrade head`. Создаются
таблицы и загружается 21 футбольная площадка СВАО. Слоты и пользователи
искусственно не добавляются.

Проверить состояние:

```bash
docker compose ps
docker compose logs --tail=100 backend bot notification-worker
```

При корректных настройках сервисы `postgres`, `backend`, `bot`,
`notification-worker` и `miniapp` работают без постоянных перезапусков.

### 3. Проверить локально

- mini-app: <http://localhost:8080>;
- OpenAPI: <http://localhost:8000/docs>;
- список площадок: <http://localhost:8000/fields>.

Обычный браузер не передаёт подписанный `initData`, поэтому просмотр списка игр
работает, а запись, создание, отмена и «Мои игры» вернут `401`. Полный сценарий
нужно проверять из MAX.

## Подключение к MAX

1. Создайте бота на платформе MAX и получите токен.
2. Создайте mini-app для этого бота.
3. Запустите проект на порту `8080`.
4. Опубликуйте порт через HTTPS, например:

   ```bash
   cloudflared tunnel --url http://localhost:8080
   ```

5. Скопируйте выданный адрес вида `https://<id>.trycloudflare.com`.
6. Укажите его как URL mini-app в настройках бота на платформе MAX.
7. Запишите этот же URL в `MAX_MINI_APP_URL` в `.env`. Непустое значение
   включает кнопку `open_app` в приветствии бота.
8. Пересоздайте бота:

   ```bash
   docker compose up -d --force-recreate bot
   ```

9. Откройте бота в MAX и нажмите «Начать» или отправьте `/start`.

Бот работает через Long Polling и обращается к
`https://platform-api2.max.ru`. Для стенда должен быть разрешён исходящий
HTTPS-доступ к этому адресу. Быстрый URL Cloudflare меняется после перезапуска
туннеля; новый адрес нужно снова указать в MAX и `.env`.

Frontend загружает официальный MAX WebApp Bridge с
`https://st.max.ru/js/max-web-app.js`. Bridge передаёт данные пользователя,
сигнал готовности и кнопку «Назад». Если этот ресурс недоступен, публичный
список игр откроется, но защищённый пользовательский сценарий работать не
будет.

Mini-app передаёт `window.WebApp.initData` в заголовке `X-Max-Init-Data`.
Backend проверяет HMAC-подпись тем же `MAX_BOT_TOKEN`, срок действия и извлекает
ID пользователя. Своей регистрации и таблицы пользователей нет.

## Основной сценарий проверки

Для полного сценария нужны два аккаунта MAX: организатор и игрок.

1. Организатор открывает бота, запускает mini-app и проходит онбординг.
2. Нажимает «Создать игру».
3. Выбирает площадку, время в будущем, минимум и максимум игроков, затем
   публикует игру.
4. Ожидаемый результат: игра появляется в общем списке и в «Моих играх» с
   ролью организатора.
5. Игрок открывает эту игру и нажимает «Записаться».
6. Ожидаемый результат: состав увеличивается, игра появляется в «Моих играх»,
   а бот присылает «Вы записаны на игру».
7. Игрок нажимает «Отказаться от участия».
8. Ожидаемый результат: место снова свободно, будущие напоминания игрока
   отменяются, организатор получает сообщение об освободившемся месте.
9. Игрок снова записывается, после чего организатор отменяет игру.
10. Ожидаемый результат: игра исчезает из активного списка, участник получает
    сообщение об отмене.

Дополнительные проверки:

- повторная запись возвращает конфликт;
- запись в заполненную игру невозможна;
- запись в пересекающуюся игру невозможна;
- контакт организатора виден только записавшимся участникам;
- за 24 часа и 2 часа до игры приходят напоминания;
- за час бот сообщает, набран ли минимальный состав.

Примеры сообщений:

```text
Вы записаны на игру.

29.09.2026, 20:00–21:30
Парк спорта Яуза, Москва, парк спорта Яуза
```

```text
Игра подтверждена — минимум участников набран.
```

```text
Игра отменена хостом.
```

## Данные

Рабочая PostgreSQL содержит четыре таблицы:

- `fields` — название, адрес, район и активность площадки;
- `slots` — площадка, организатор, время, состав, мяч, контакт и отмена;
- `participations` — запись MAX user ID на слот;
- `notification_jobs` — получатель, тип, время, статус, попытки и ошибка
  отправки.

Миграции:

1. `20260923_0001` — основная схема;
2. `20260928_0002` — 21 площадка СВАО;
3. `20260929_0003` — очередь уведомлений;
4. `20260929_0004` — добавление организаторов существующих игр в список
   участников.

Время хранится с часовым поясом, сообщения форматируются по
`Europe/Moscow`. Зависимость `tzdata` включена в backend.

При локальном запуске данные сохраняются в Docker volume `postgres_data` и
переживают `docker compose down`. На рабочем стенде данные хранятся в отдельной
управляемой PostgreSQL Render. Тесты используют PostgreSQL в `tmpfs`; после
удаления тестового контейнера тестовые данные исчезают.

## Уведомления и отказы внешних сервисов

API не отправляет сообщения в MAX напрямую. При записи на игру, отказе или
отмене оно создаёт задание в таблице `notification_jobs`. Отдельный процесс
`notification-worker` забирает готовые задания, формирует текст и вызывает MAX
Bot API. Обычный процесс `bot` эту очередь не обрабатывает.

Worker обрабатывает задания со статусами `pending`, `processing`, `sent`,
`failed` и `canceled`. При временной ошибке MAX API задача возвращается в
очередь с увеличивающейся задержкой. После пяти неудачных попыток по умолчанию
она получает статус `failed`.

Если MAX API недоступен:

- API и база продолжают работать;
- действия пользователя сохраняются;
- уведомления остаются в очереди и повторяются worker-ом;
- диагностика доступна через
  `docker compose logs --tail=200 notification-worker`.

### Worker на Render

Для постоянной отправки уведомлений нужен отдельный **Background Worker** из
`render.yaml` (New → Blueprint) либо созданный вручную с теми же параметрами:

| Параметр | Значение |
| --- | --- |
| Runtime | Docker, `backend/Dockerfile`, context `backend` |
| Docker command | `python -m app.notification_worker` |
| `DATABASE_URL`, `MAX_BOT_TOKEN` | те же значения, что у API |
| `NOTIFICATION_*` | см. `.env.example` (значения по умолчанию подходят) |

Если worker не запущен, задания остаются в PostgreSQL и сообщения пользователям
не приходят. Бот на Long Polling для рассылки не нужен: его можно остановить, а
уведомления продолжат доставляться.

Создание `render.yaml` само по себе не запускает worker: Blueprint нужно
добавить в панели Render и передать ему `DATABASE_URL` и `MAX_BOT_TOKEN`. До
этого worker необходимо держать запущенным локально.

Миграции применяет только API (`alembic upgrade head` в команде запуска). Worker
сам ничего не мигрирует: при старте он ждёт, пока версия схемы в
`alembic_version` совпадёт с последней миграцией образа, и пишет в лог
`Waiting for migrations`. Так на первом деплое не возникает гонки и ошибок
`relation "notification_jobs" does not exist`. Render перезапускает упавший
worker сам; при остановке (SIGTERM) worker дорабатывает текущее сообщение, а
нетронутые задания возвращает в очередь. Если в локальной базе нет таблицы
`notification_jobs`, пересоберите образы: `docker compose up --build -d`.

### Статусы, повторы и наблюдение

| Статус | Значение |
| --- | --- |
| `pending` | ждёт `scheduled_at` или повторной попытки |
| `processing` | взято worker-ом |
| `sent` | доставлено (`sent_at`) |
| `failed` | попытки исчерпаны, причина в `last_error` |
| `canceled` | отменено (игра отменена или участник вышел) |

- Ошибка отправки: повтор через 60, 120, 240, 480 с (далее 960 с), всего
  `NOTIFICATION_MAX_ATTEMPTS` попыток; `last_error` содержит тип ошибки и тело
  ответа MAX.
- Задание, зависшее в `processing` дольше `NOTIFICATION_LOCK_TIMEOUT_SECONDS`
  (worker упал), возвращается в `pending`; потеря блокировки считается попыткой,
  поэтому «ядовитое» задание в итоге станет `failed`.
- Раз в `NOTIFICATION_STATS_INTERVAL_SECONDS` в лог пишется строка
  `Notification queue: pending=… processing=… sent=… failed=… canceled=… due=… oldest_due_lag=…`;
  если очередь отстаёт больше 5 минут, уровень — `WARNING`. Каждая неудачная
  попытка — `WARNING`, окончательный отказ — `ERROR` с id задания, типом и
  получателем.

Состояние очереди и последние ошибки можно посмотреть SQL-запросами:

```sql
SELECT status, count(*) FROM notification_jobs GROUP BY status;

SELECT id, notification_type, recipient_user_id, attempts, last_error, scheduled_at
FROM notification_jobs
WHERE status = 'failed' OR last_error IS NOT NULL
ORDER BY id DESC LIMIT 20;
```

### Smoke-тест доставки

Пользователь должен хотя бы раз открыть диалог с ботом. Скрипт создаёт по одному
заданию каждого типа (`joined`, `reminder_24h`, `reminder_2h`,
`game_status_1h`, `slot_canceled`, `participant_left`) для указанного
пользователя и ждёт, пока работающий worker их отправит:

```bash
docker compose exec backend python -m app.notification_smoke --user-id <MAX_USER_ID>
```

На Render запустите ту же команду в Shell сервиса API. Код возврата `0` — все
шесть сообщений получили статус `sent`. Сквозную проверку триггеров выполните
по разделу «Основной сценарий проверки».

## Переменные окружения

Основные:

- `MAX_BOT_TOKEN` — токен бота; обязателен для авторизации, бота и уведомлений;
- `MAX_MINI_APP_URL` — публичный URL mini-app; непустое значение включает
  кнопку открытия приложения;
- `DATABASE_URL` — подключение backend и worker к PostgreSQL;
- `CORS_ORIGINS` — разрешённые origin через запятую;
- `MAX_AUTH_MAX_AGE_SECONDS` — срок действия `initData`, по умолчанию 3600.

Порты:

- `MINI_APP_PORT` — mini-app/nginx, по умолчанию `8080`;
- `BACKEND_PORT` — FastAPI, по умолчанию `8000`;
- `POSTGRES_PORT` — PostgreSQL на хосте, по умолчанию `5432`.

Worker:

- `NOTIFICATION_POLL_INTERVAL_SECONDS` — пауза пустого цикла, по умолчанию 10;
- `NOTIFICATION_BATCH_SIZE` — задач за итерацию, по умолчанию 50;
- `NOTIFICATION_MAX_ATTEMPTS` — максимум попыток, по умолчанию 5;
- `NOTIFICATION_LOCK_TIMEOUT_SECONDS` — возврат зависшей задачи, 300 секунд;
- `NOTIFICATION_RETRY_DELAY_SECONDS` — базовая задержка повтора, 60 секунд;
- `NOTIFICATION_STATS_INTERVAL_SECONDS` — период строки со статистикой очереди
  в логе, 60 секунд.

Если порт `5432` занят, измените только внешний порт:

```env
POSTGRES_PORT=5433
```

Внутренний `DATABASE_URL` при запуске через Compose должен по-прежнему
содержать `postgres:5432`.

## Тесты

Полный набор backend-тестов запускается одной командой в изолированном
окружении:

```bash
docker compose --profile test run --rm --build backend-test
```

Очистить тестовый контейнер:

```bash
docker compose --profile test rm -sf test-postgres
```

Тесты применяют миграции к отдельной временной базе и не меняют рабочие данные.
Они проверяют API, подпись MAX, создание и отмену слотов, запись, пересечения,
конкуренцию за последнее место, приватность контакта и worker уведомлений.

## Диагностика

`bot` или `notification-worker` постоянно перезапускается:

```bash
docker compose logs --tail=100 bot notification-worker
```

Чаще всего не задан или неверен `MAX_BOT_TOKEN`.

Кнопки открытия mini-app нет — проверьте непустой `MAX_MINI_APP_URL` и
пересоздайте сервис `bot`.

Mini-app показывает ошибку входа — приложение должно быть открыто из MAX;
обычная вкладка браузера не содержит `initData`. Также проверьте, что токен
backend совпадает с токеном бота.

Backend не подключается к базе — дождитесь статуса `healthy` у `postgres` и
проверьте `DATABASE_URL`:

```bash
docker compose ps
docker compose logs --tail=100 postgres backend
```

Порт уже занят — измените соответствующий `*_PORT` в `.env` и пересоздайте
контейнеры.

## Остановка и повторный запуск

Остановить без удаления контейнеров:

```bash
docker compose stop
```

Повторно запустить:

```bash
docker compose start
```

Удалить контейнеры и сеть, сохранив базу:

```bash
docker compose down
```

Пересобрать после изменения кода или переменных сборки:

```bash
docker compose up --build -d
```

Полностью удалить рабочую базу и начать с чистого состояния:

```bash
docker compose down -v
docker compose up --build -d
```

Команда с `-v` необратимо удаляет все слоты, записи и очередь уведомлений.
Площадки загрузятся повторно миграцией.

## Зависимости

Файлы зависимостей присутствуют:

- `backend/requirements.txt` — Python-библиотеки с точными версиями;
- `frontend/package.json` — зависимости и команды frontend;
- `frontend/pnpm-lock.yaml` — точные версии и контрольные суммы frontend;
- `compose.yaml` и Dockerfile-ы — версии базовых образов и воспроизводимая
  сборка.

Frontend собирается командой `pnpm install --frozen-lockfile`, поэтому Docker
не изменяет lock-файл во время проверки.

## Ограничения MVP

- только футбол и только площадки СВАО;
- слоты показываются на ближайшие семь дней;
- карт, геолокации, платежей и бронирования площадок нет;
- список площадок хранится внутри проекта и не обновляется внешним API;
- отдельной базы профилей пользователей нет — используются ID из MAX;
- организатор автоматически добавляется в участники своей игры и входит в
  счётчик набранного состава;
- участники в управлении игрой показываются без имён, поскольку профили MAX в
  собственной базе не хранятся;
- изменение уже опубликованного слота и произвольная рассылка организатора из
  интерфейса пока не реализованы;
- время в форме вводится в локальном часовом поясе устройства, затем
  отправляется на сервер в UTC;
- бот работает через Long Polling, webhook не реализован;
- публичный HTTPS-туннель не входит в Docker Compose;
- активные игровые слоты не добавляются автоматически: первый слот создаётся
  через интерфейс.
